# Current implementation contract

Authoritative models, canonical JSON and hashing primitives are in `src/shared.ts`. The catalog directory format and index schema are in `src/catalog/model.ts` with zod validation in `src/catalog/schemas.ts`. Node >=22.13.0 is required. The terminal user is anonymous and needs no account. There is no self-hosted server: skill content is distributed from a GitHub catalog repository.

## Hybrid retrieval (phased)

Search is a local, two-channel operation over the cached catalog index. Channel one is keyword scoring over each entry's summary (id, name, description, category, tags). Channel two is semantic vector scoring, shipped as an optional `semantic` section inside `index.json`:

- Vectorized inputs: the skill's capability text (name, description, tags, category, weighted heaviest) and its body text (entry file plus bundled text files). Source URLs — GitHub addresses and any other links — are stripped before tokenization and never contribute to vectors; they remain source metadata in manifests and audit records only.
- Phase 1 model (`hashed-tfidf/v1`): deterministic, dependency-free hashed TF-IDF projection into 128 signed dimensions, plus a term-centroid table. `skillflux catalog build` computes it from version-directory content; `--check` reproduces it byte-for-byte.
- Query embedding is offline: query terms are embedded by summing stored term centroids, so no model ships with the client and no network call is ever made for search. A query term with morphology shifted from the indexed form still lands near its target because tokenizer prefixes and CJK n-grams share centroids.
- Scoring: `0.45 × keyword + 0.55 × semantic` when a query vector exists; a semantic hit alone (>= 0.18 cosine) can surface a skill the keyword pass missed. Indexes without a `semantic` section, and clients that predate the field, degrade to unchanged keyword-only behavior — the section is additive and ignored by `fetchIndex`'s schema check.
- Phase 2 (reserved): the `model.kind` string versions the scheme. A future `embedding/v1` section may replace vectors with real embedding-model output computed at catalog build time; the same offline term-centroid query path keeps working because centroids are rebuilt in that space. Client search code needs no change.

## Catalog repository layout

```
skills/<category>/<id>/<version>/
├── skillflux.json          # declarative manifest (id, version, entry, deps, permissions, hosts, release)
├── skillflux.review.json   # review record + evaluation evidence bound to the content hash
└── SKILL.md and other text content files
index.json                  # generated by `skillflux catalog build`; the client's only entry point
```

`skillflux catalog build ROOT` scans every version directory, runs the automated checks, recomputes per-file sha256/size, verifies the review sidecar's `evaluation.contentHash` binding against the directory content, derives qualification, and writes `index.json`. `skillflux catalog build --check ROOT` fails when the committed index does not match the directory content — this is the CI consistency gate for the catalog repository.

Qualification derivation (identical semantics to the previous server gate): `approved` status + automated checks passed + `kind: "human"` evaluation bound to the current `contentHash` with passing purpose and boundary cases and installed+read evidence covering every declared host. `simulation` evidence never qualifies a version. Revocation changes the review status to `revoked`; dependents recursively lose their derived qualification.

## Trust and transport

There are no Ed25519 signatures. Trust anchors are: the GitHub account (2FA + branch protection, configured repository-side), HTTPS, commit-SHA pinning and per-file sha256. `init` resolves the default branch head to a 40-hex commit SHA via the GitHub API; every index and file download is then served from `raw.githubusercontent.com/<owner>/<repo>/<sha>/...` (or a mirror passed via `--source`). Redirects are rejected; response sizes and timeouts are bounded.

Local `search` runs entirely over the cached catalog index (24-hour TTL per project); capability queries never leave the machine. Plans are HMAC-sealed with a per-project secret, expire, and bind exact package digests, the project, the repository and host. Installation downloads each declared file and verifies size and sha256 against the index entry before anything is written.

## CLI

`skillflux catalog PATH [--check] [--output FILE]`, `init --project PATH [--repo OWNER/NAME] [--source URL] --host codex|claude|cursor|generic [--preauthorize-reviewed-text] [--update-policy manual|follow-compatible]`, `serve`, `search`, `plan`, `install`, `load`, `list`, `check-updates`/`outdated`, `update-policy [manual|follow-compatible] --project PATH`, `pin`/`unpin`, `update [SKILL@VERSION] [--plan PLAN_ID] [--yes]`, `rollback`, `remove`, `privacy [status] [--reset-trust]`. Host MCP files are `.codex/config.toml`, `.cursor/mcp.json`, or `.mcp.json` for Claude/generic; the bootstrap skill is explicit-only in every host.

`install` executes only install/reinstall plans. MCP-channel installation additionally requires the local `--preauthorize-reviewed-text` consent; a model-provided boolean cannot supply it. Manual version changes require an exact update plan reviewed by the user, even when automatic following is enabled. `update` without an exact target is read-only. `check-updates` uses the 24-hour catalog index cache and reports unknown status honestly when offline; installation, upgrades and rollback require a reachable catalog. Rollback restores a previously verified lock state, re-checks revocations and, when following is enabled, pins restored versions so the next load cannot immediately upgrade them again. Local edits and pins block destructive changes; edited files are preserved on removal.

The local policy field `updatePolicy` is `manual` by default, including for existing policy files that omit it. The user may explicitly set `follow-compatible` during init or through the local `update-policy` command. This authorization is independent of initial installation preauthorization. Before returning content, `load` can automatically execute a validated exact update plan under this policy. Eligible releases are approved and qualified UTF-8 text packages, stable, compatible with the current host/runtime, in the installed major version (same minor for `0.x`), and do not cross breaking releases. Full dependency resolution and verification apply; new dependencies must satisfy the reviewed text and non-breaking constraints. Pins, local modifications, publisher, maintainer or permission changes, incompatible dependencies and revoked targets block following. Failed updates preserve the installed state. Offline loading can return locally reverified content with an unknown catalog status; known revocations and local tampering still fail closed.

`LoadedSkill.autoUpdate` reports `{ mode, status, fromVersion, toVersion?, reason?, changes? }`, where `status` is `manual | current | updated | blocked | unknown` and each change is `{ id, from, to }`. This reports the content-following outcome, not an npm program update. Client binaries and bootstrap changes require installing a new npm package, rerunning init with the same repository/host and restarting MCP. No background daemon or push synchronization is installed.

Installed packages keep the same safety envelope as before: UTF-8 text only, at most 512 KiB / 64 files, per-file hashes, no shell/network/secret permissions, no reserved runtime filenames (`manifest.json`, `.skillflux-*.json`, `skillflux.json`, `skillflux.review.json` — the latter two are stripped from installed copies). Install anchors are local `.skillflux-manifest.json` records; every load re-verifies each file byte-for-byte and rejects symlinks, undeclared files and tampering. Installations remain transactional (staging → journal → atomic rename → lock history) with journal recovery on next open.

## MCP tools

`skillflux.search`, `skillflux.plan`, `skillflux.install`, `skillflux.load`, `skillflux.list`, `skillflux.check_updates`, `skillflux.pin`, `skillflux.update`, `skillflux.rollback`, `skillflux.remove`, `skillflux.privacy` (read-only). Advertising no longer exists anywhere in the protocol: no ad fields, no ad events, no house ads. Revocation information comes from the catalog index status/qualification fields.

`skillflux.load` advertises `readOnlyHint: false` because an authorized automatic update may write packages and the lock. Its text response describes the automatic update outcome and any blocking reason before the skill body; the same outcome is included in structured content. No MCP tool can change the persistent update policy. `skillflux.update` always retains exact-plan user approval; automatic following is confined to `load` and the locally configured policy.

## Static website

Public pages use a validated snapshot synced from the GitHub catalog repository. `publication:sync` resolves the head commit, downloads `index.json` plus every approved+qualified skill's files at that SHA, verifies per-file hashes and writes a `skillflux-publication/v2` snapshot: `{ schema, repo, commitSha, fetchedAt, items }`. `publication:build` atomically switches a complete snapshot+dist release keyed by commitSha; failed builds preserve the previous release. Revoked or needs-testing entries are not synced as installable content. Any approval, retest or revocation requires sync + rebuild + redeploy to change public HTML.
