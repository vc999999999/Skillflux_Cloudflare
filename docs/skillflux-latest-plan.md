# SkillFlux 最新完整计划

更新日期：2026-10-08（增加项目级授权自动跟随内容更新）
文档用途：统一产品定位、功能范围、技术架构、业务规则和完整验收标准。

本文保存已确认的产品方案与架构约束。实现状态以代码和 [验证记录](verification.md) 为准；计划中的目标不等于已经发布或上线。

## 1. 执行摘要（Executive Summary）

### 1.1 要解决的问题

Skill 来源分散，用户难以判断哪些适合自己的任务、哪些经过实际测试，以及安装后如何维护。用户不希望为了使用不同能力而预先下载大量 Skill；希望一次授权后跟随维护者的兼容更新，同时保留固定版本、保护本地修改和随时关闭自动更新的能力。

SkillFlux 提供两层能力：公开静态网站负责整理和发现；npm + MCP 负责在用户明确调用后，从 GitHub 精选目录仓库搜索经过质检、专人维护的精品 Skill，并按需加载到项目。

### 1.2 已确认的产品决策

| 事项 | 最新决定 |
| --- | --- |
| 网站定位 | 静态 Skill 来源黄页、场景选型内容与精品版本目录，供人和检索系统阅读 |
| 原有文章 | 整合到“场景与选型”；保留有价值的内容与旧 URL，不能把编辑分析写成人工实测 |
| 精品分发 | 一个 SkillFlux npm 入口 + 本地 MCP + **GitHub 目录仓库**（`skillflux-catalog`），显式调用、按需搜索与下载 |
| 内容维护 | 平台挑选并维护；审核记录以 `skillflux.review.json` 旁挂文件随目录提交，`index.json` 由本地 `skillflux catalog build` 生成 |
| 内容信任 | 免 Ed25519 签名：信任根为 GitHub 账号（2FA + 分支保护）+ HTTPS + 逐文件 sha256 + CI 一致性检查 |
| 普通用户账号 | 不需要注册、登录、会员或个人中心 |
| 内容更新 | 默认手动；用户可一次开启兼容版本自动跟随，在加载前同步；只读检查保持独立 |
| 收入来源 | **广告系统已移除**（2026-10-01 决策）：不再有广告投放、计费、咨询与举报后端；后续如需商业化另立决策 |
| 运营权限 | 通过 GitHub 仓库权限与 PR 工作流管理；不再有运营台和运营 token |
| 工程划分 | `web/` 与 `mcp/` 两个独立目录；运行数据不能混入网页或 npm 发布产物 |
| 交付要求 | 完整实现、真实接口、完整异常处理和实际验证；不是只完成首页或原型 |

### 1.2.1 架构改造决定（2026-10-01）

自托管 Registry（HTTP API + SQLite + Ed25519 签名 + 广告计费 + 运营台）整体移除，替代架构：

- **GitHub 目录仓库是技能内容唯一来源**。每个版本一个目录 `skills/<category>/<id>/<version>/`，含声明性 `skillflux.json`、旁挂审核 `skillflux.review.json` 和内容文件；根级 `index.json` 由 `skillflux catalog build` 从目录内容生成。
- **客户端按 commit SHA 钉死下载**。init 时解析默认分支当前 commit，index.json 与全部文件都从 `raw.githubusercontent.com/<owner>/<repo>/<sha>/...` 拉取；历史不可变性由 git 历史与 SHA 不可伪造性保证。
- **搜索本地化**。客户端缓存 index.json（24 小时）后本地过滤，搜索词不再离开本机。
- **网站构建从目录仓库取数**。同步脚本拉 index + 文件生成 publication v2 快照，页面渲染逻辑零改动。
- **撤销/资格语义保留**。`skillflux.review.json` 的 `status` 字段 + qualification 派生规则（approved + 人工评测绑定 contentHash + hosts 覆盖）与原 Registry 门禁等价；版本仍不可变（同一 `<id>/<version>/` 目录内容只能以新版本变更）。

### 1.3 核心使用场景

1. 用户在自己的项目安装 SkillFlux npm 包并初始化宿主配置（`init --repo <owner>/skillflux-catalog`）。
2. 用户明确调用 SkillFlux，描述需要的能力。
3. AI 通过本地 MCP 在缓存的目录索引中搜索经过挑选、质检和维护的 Skill（搜索词不出本机）。
4. 用户或既有项目授权策略允许安装后，运行时按明确版本逐文件下载、校验 sha256、安装并更新项目锁。
5. 运行时把需要的 Skill 正文和资源返回当前会话，宿主 AI 用它完成用户任务。
6. 后续加载按本地策略处理更新：默认仅提示；用户已开启自动跟随时，在返回正文前同步符合策略的兼容稳定版。超出策略范围的变更仍需明确批准精确计划。

网站不是线上 AI 工作台，不负责直接读写访客电脑中的项目。

### 1.4 成功标准

- 核心公开内容在构建后的 HTML 中完整存在，禁用 JavaScript 仍能阅读和访问详情。
- npm 包能在干净项目安装，并通过真实 stdio MCP 完成搜索、计划、授权安装和同轮加载。
- 所有公开 Skill 正文、清单、资源和下载入口执行一致的版本资格与撤销检查。
- 完整功能、类型检查、打包、静态发布与浏览器操作有可复现的验收证据。

搜索收录量与 AI 引用量属于上线后的实际经营指标，不预填数字，也不保证收录、排名或模型采用。

## 2. 用户体验与功能（User Experience & Functionality）

### 2.1 角色与用户故事

| 角色 | 用户故事 | 验收条件 |
| --- | --- | --- |
| 网站访客 | 我想按来源、用途和标签查找 Skill 信息，以便决定下一步去哪里了解 | 来源目录、分类、标签、详情、搜索和筛选可用；明确收录不等于质检 |
| 项目使用者 | 我只想接入一个 SkillFlux，在需要时获取合适能力 | 入口显式触发，搜索本地缓存索引，不预装整个库；下载与加载作用于指定项目 |
| 已安装用户 | 我希望一次开启自动跟随，也能固定版本或随时关闭 | 加载前同步符合策略的兼容内容；只读检查、手动更新、固定版本和本地修改保护有效 |
| 目录维护者 | 我想查看完整内容和测试记录后决定发布或撤销 | 仓库 PR 展示完整 diff；审核记录（`skillflux.review.json`）与内容绑定，CI 校验 index 一致性 |

### 2.2 公开网站信息架构

| 页面/入口 | 主要内容与行为 |
| --- | --- |
| `/`、`/en/` | 产品定位、来源搜索、来源分类、目录入口、场景选型、精品快照与接入说明 |
| `/directory/` | 完整来源黄页，关键词、来源分类、地域/语言维度和信任标签筛选 |
| `/category/:slug/` | 某一来源分类的静态聚合页 |
| `/tag/:tag/` | 某一标签的静态聚合页 |
| `/site/:slug/` | 外部来源介绍、原始链接、标签、维护时间、关联来源和收录边界 |
| `/registry/` | 精品 Skill 静态快照，关键词、能力分类、宿主、排序、分页与详情链接 |
| `/skills/:id/` | 当前最高合格版本；如果没有可用版本，展示公开状态，不冒充可安装内容 |
| `/skills/:id/versions/:version/` | 固定版本详情、变更、质检摘要、资源和安装命令；不可用版本保留状态说明 |
| `/scenarios/` | “场景与选型”内容入口 |
| `/scenarios/:slug/` | 来源比较、按需接入、版本维护等具体指导，关联目录和接入步骤 |
| `/guides/`、`/insights/` | 保留已有指南、分析文章及有价值的旧 URL |
| `/setup/` | npm 获取、项目初始化、宿主配置、显式调用、授权、更新与排错说明 |
| `/quality/` | 质检标准、人工评测与自动检查的区别、版本资格和撤销规则 |
| `/contact/`、`/privacy/`、`/terms/` | 平台联系、数据用途、权限边界和使用说明 |
| 404 页面 | 明确不存在的地址，提供返回目录的路径，不跳转成其他 Skill 版本 |

公开核心页面提供中英文界面。原始 Skill 文本、维护者摘要和仅中文的已有文章保留原语言，不伪造翻译或评测；语言切换应说明实际内容语言并保留筛选条件。

`/advertise/`、`/report/` 与 `/console/` 已随广告系统和运营台下线。当前 Worker 不实现这些旧业务路由；商务联系使用 GitHub Issue 或邮件链接。

### 2.3 黄页、精品与文章的关系

- 黄页是外部来源索引。收录、推荐标签和来源信任标签不证明其中每个 Skill 已经通过平台测试。
- 精品库是平台管理的具体版本集合，必须通过版本级质检，才提供可安装正文和资源。
- 文章是解释、比较和使用指导。文章引用某个 Skill，不等于批准该 Skill 进入精品库。
- 没有合格精品时，展示真实空状态，并允许继续浏览来源黄页；不能拿开发样例填充精品目录。

### 2.4 网站搜索与交互

- 来源黄页在静态数据上筛选；精品目录在同步自 GitHub 目录仓库的静态发布快照上筛选。
- 搜索、分类、宿主、排序和分页状态使用 URL 参数，可复制、刷新恢复，并支持浏览器前进后退。
- 切换语言保留相关查询参数；清除筛选回到完整集合，不删除无关追踪参数。
- 提供正常、空结果、不可用、加载中、失败、重试、操作成功与复制失败反馈。
- 不依赖 JavaScript 才生成主要条目；JavaScript 只增强交互。
- 详情页复制固定版本命令，不自动下载或修改用户电脑。
- 支持键盘、可见焦点、跳转正文、移动端导航和窄屏换行；不能靠隐藏溢出裁掉必要内容。

### 2.5 精品版本详情

每个公开版本至少包含：

- 名称、标识、版本、用途、分类、标签、维护者和许可证。
- 支持的宿主、权限声明、精确依赖、入口文件和内容摘要值。
- 变更摘要、破坏性变更提示、最低客户端版本和维护时间；历史缺失字段如实标记。
- 自动检查结果、人工实测公开摘要、用途/边界测试与宿主检查信息。
- 该版本的完整文本资源，作为文字展示，不在页面中执行。
- 固定版本安装命令、版本历史、相关接入和更新维护入口。
- 静态快照时间及“安装和加载仍需检查目录仓库当前状态”的说明。

撤销或待补测版本不展示可安装正文和下载入口，只展示允许公开的状态、原因及其他合格版本入口。

### 2.6 目录仓库维护流程（替代运营台）

审核与发布通过 GitHub 仓库工作流完成：

1. 维护者在本地技能目录中修改内容文件（同一 `<id>/<version>/` 目录内容不可变，内容变更必须新增版本目录）。
2. 运行 `skillflux catalog build`：自动扫描（路径安全、扩展名、secret 模式、保留名）、计算逐文件 sha256、校验 `skillflux.review.json` 与内容绑定、派生 qualification、重新生成 `index.json`。
3. 审查 `git diff` 后提交 PR；`kind: simulation` 的评测记录不能使版本获得 qualified 资格，与原门禁一致。
4. CI 运行 `skillflux catalog build --check`：`index.json` 与目录内容不一致即失败——这是免签名模型下的主要完整性防线。
5. 仓库需配置分支保护（禁 force-push、要求 PR 评审）与账号 2FA；这些是 GitHub 侧设置，不由代码自动完成。

`skillflux.review.json` 记录 status（approved/rejected/revoked/needs-testing）、reviewer、notes、人工评测（绑定 contentHash 的用途/边界/宿主检查）。撤销改为把该版本目录的 review status 改为 revoked 并重建 index；依赖该版本的合格版本派生状态随之失效，派生规则与原 Registry 门禁等价。

### 2.7 非目标与禁止替代

不建设普通用户注册登录、会员系统、广告主自助账号、在线支付或公开作者投稿；不建设线上 AI 执行工作台；不自动下载全部 Skill；不在未授权时更新项目；不保证第三方模型输出广告或搜索系统收录内容。

这些是已确认的边界，不是为了减少实现量临时删减的功能。

## 3. AI 与 Skill 系统要求（AI System Requirements）

### 3.1 npm 入口与显式调用

npm 包提供 CLI、项目级 Bootstrap Skill 和本地 stdio MCP。用户只需要接入一个 SkillFlux 入口（`init --repo <owner>/skillflux-catalog`），再通过它搜索和加载 GitHub 目录仓库中的能力。

初始化必须限定在用户指定项目，保留无关宿主配置，不能覆盖用户其他 MCP 服务或写入不必要的全局配置。支持 Codex、Claude、Cursor 和通用宿主；各宿主需要显式启用并调用入口，不能假设新下载的文件会立刻被宿主自动发现。

MCP 工具职责：

| 工具 | 职责 |
| --- | --- |
| `skillflux.search` | 在本地缓存的目录索引中搜索合格版本，返回匹配理由和可供选择的信息；搜索词不出本机 |
| `skillflux.plan` | 解析明确版本和依赖，生成绑定项目、权限、锁状态与有效期的计划 |
| `skillflux.install` | 在项目授权策略允许时安装计划；逐文件下载并校验 sha256、资格与撤销 |
| `skillflux.load` | 校验已安装内容；本地策略已开启时先同步合规的兼容稳定版，再返回入口、资源和更新摘要；不执行脚本 |
| `skillflux.list` | 查看项目已安装版本和状态 |
| `skillflux.check_updates` | 只读检查当前与可用版本、兼容信息、变更和缓存新鲜度 |
| `skillflux.pin` | 明确设置或解除版本固定策略 |
| `skillflux.update` | 只执行用户明确批准的精确升级计划，不隐式解析任意最新版 |
| `skillflux.rollback` | 在安全资格与本地保护检查通过后回滚，在开启跟随时固定恢复的版本以防下次加载立即升回 |
| `skillflux.remove` | 按项目范围移除指定内容，保护无关文件 |

初次安装的项目级纯文本预授权必须由用户明确设置；AI 传入一个“用户已同意”的布尔值不构成权限依据。它与 `updatePolicy` 独立：默认 `manual`；用户可通过本地 `init --update-policy follow-compatible` 或 `update-policy follow-compatible` 一次授权兼容版本跟随。MCP 不提供修改持久更新策略的工具。手动 `skillflux.update` 仍要求明确批准精确计划，自动跟随不能授权任意破坏性升级。项目策略文件受运行时校验与符号链接保护，但对拥有同等文件权限的宿主 AI 不构成强边界；授权模型的目标是防止 SkillFlux 自身静默变更，而不是防御有意的本地篡改。

### 3.2 质检与人工维护

发布前必须同时满足：

1. 自动安全检查通过：文件路径、格式、体积、哈希、入口、权限与依赖符合策略（`skillflux catalog build` 内置扫描）。
2. 许可与再分发核验通过：声明许可证允许平台再分发全文，或已取得来源方授权；不允许再分发的内容只能进入黄页索引，不能进入精品库。
3. 真实人工用途测试通过：记录输入、预期、实际结果、执行方法与证据。
4. 真实人工边界测试通过：覆盖不适用情况、失败情况与能力限制。
5. 每个声明宿主都有安装和读取验证；不能声称没有测试过的宿主支持。
6. 测试记录绑定当前提交内容的 `contentHash`。
7. 维护者完成独立批准操作（`skillflux.review.json` 的 status/ reviewer / notes），决定可公开的摘要。

自动扫描不代表效果测试。`simulation` 可以留档，但不能满足真实发布门槛。最新人工测试失败时，不能跳过它、选用更早的通过记录继续批准。

测试程序可以在隔离的临时目录仓库中模拟审核输入，以验证工作流；这类记录必须明确标识为合成测试材料，不能进入生产目录仓库，也不能对外宣传为真实专人实测。

### 3.3 不可变版本与历史补测

- 已发布版本目录内容不可覆盖；内容改变必须发布新版本目录。
- 依赖必须是明确版本且当前合格；不允许安装依赖不合格的上层包。
- 同一计划内同一依赖出现不同版本要求时解析失败并明确报错，不做隐式版本选择；不存在同一项目同时安装同一 Skill 两个版本的语义。
- 撤销应递归影响固定依赖它的版本，所有公共资源入口使用一致门禁。
- 历史 `approved` 版本缺少当前要求的评测时，标记为 `needs-testing` 并停止提供可安装正文。
- 历史版本允许补充真实评测（更新 `skillflux.review.json` 的 evaluation 并绑定当前 `contentHash`）再次批准，恢复同一版本资格；不得强迫通过修改原版本目录或新发版本来回避补测需求。
- 私人测试输入、输出、环境和维护者笔记不进入公开目录仓库；公开 review 文件只含可公开摘要。
- 如果旧版本目录本身已经包含不应公开的信息，不能同时“改内容脱敏”和“保持原摘要”；应撤销旧版本，并以新版本发布脱敏内容。

### 3.4 自动跟随、手动升级和离线

项目策略由用户一次选择，更新检查与实际执行保持可区分：

- 新旧项目默认 `manual`；显式选择 `follow-compatible` 后，CLI / MCP 每次 `load` 在返回正文前尝试在线更新，不需要每次重复批准符合策略的更新。
- 自动跟随仅接收同 major 的稳定版，`0.x` 限于同 minor 的补丁；目标和完整依赖须已批准、合格、兼容宿主与当前客户端，且不跨越破坏性发布。现有包的发布者、维护者和权限不得改变；新增依赖必须是已审核无破坏性变化的纯文本包。
- 自动执行复用精确计划、逐文件哈希校验和事务切换；同步的是正文、参考资料、模板等包内容，不能自动执行脚本或取得新增权限。
- `load` 返回 `autoUpdate`：模式、`manual/current/updated/blocked/unknown` 状态、前后版本、变更列表和原因。MCP 明确标记可能写文件，正文之前呈现更新结果。
- 本地 `update-policy` 无参数可查看策略，指定 `manual` 可关闭；现有用户不会因安装新客户端而被默认开启。
- `check-updates` / `outdated`（CLI 子命令，对应 MCP 工具 `skillflux.check_updates`）只读比较，不替换安装内容或项目锁中的精确版本。
- 返回当前版本、可用版本、变更摘要、破坏性变更、宿主与最低客户端兼容信息。
- 普通版本提醒允许使用最长 24 小时缓存，并显示缓存时间；主动检查可以刷新。
- 安全撤销和资格检查独立处理，不能被普通更新缓存覆盖。
- 固定版本仍能看到更新信息，但普通升级不能悄悄替换；升级前必须明确解除固定。
- 升级计划固定具体目标，执行前重新核验权限、锁状态、依赖、资格与撤销。
- 手动非交互 CLI 升级需要明确确认参数；MCP `skillflux.update` 只接受已批准计划 ID，不借用跟随策略绕过手动计划批准。
- 计划批准在 MCP 通道是约定级约束：协议无法证明用户真的审阅了计划，依赖宿主呈现计划内容并等待用户明确指令后再调用 `skillflux.update`。需要强执行时走 CLI 确认路径，不能把“AI 自行生成了计划又执行了它”视为有效授权。
- 本地编辑、文件或清单篡改、失效计划、不兼容版本和撤销状态应阻止执行；失败保留原有效状态。
- 回滚不能绕过同样的安全检查，也不能恢复已撤销或失去资格的内容；开启跟随时恢复的版本会固定，用户明确解除固定后才能继续跟随。
- 离线只允许按策略读取此前已经安装、下载时校验过 sha256 的内容，明确披露缓存与未知状态；不把未知说成“最新”或“安全状态已确认”。
- 离线时本地缓存的过期资格信息仍可加载，但必须向调用方披露信息生成时间与“当前目录仓库资格未知”；恢复在线后必须重新核验。
- 已知的资格撤回必须保留，不能用旧缓存在离线状态恢复授权。
- 应用或 MCP 没有运行时，不提供虚构的实时推送承诺。

目录仓库内容更新与 npm 客户端更新分开管理；本次实现不提供程序自更新。旧用户需先安装包含该功能的新 npm 包，使用原仓库和宿主重新运行 `init` 同步入口、重启 MCP，然后开启跟随策略。日常兼容内容更新不需要重复安装 npm 包，也没有常驻后台推送。

### 3.5 已移除的广告系统（2026-10-01 决策）

广告输出规则、预算计量、计费账本、咨询与举报后端随自托管 Registry 一并移除。产品输出不再包含任何广告字段或推广内容；后续如需商业化，须先更新本文决策再实施，不得以残留代码或隐藏开关的形式复活。

## 4. 技术规格（Technical Specifications）

### 4.1 总体架构

```text
公开访客、搜索系统、AI 检索
          │ 读取 HTML / JSON / 文本索引
          ▼
web/ 静态站与目录仓库快照（Cloudflare Workers 部署）
          ▲
          │ 同步 index + 文件 → 校验 → 构建 → 成功后发布
          │
GitHub 目录仓库 skillflux-catalog（技能内容唯一来源）
  ├─ skills/<category>/<id>/<version>/  声明 manifest、旁挂审核记录、内容文件
  └─ index.json              catalog build 生成；commit SHA 为快照锚点
          ▲
          │ HTTPS：index（解析 commit SHA 后拉取）、逐文件按需下载
          │
用户项目中的 npm Runtime + 本地 stdio MCP
  ├─ 显式 SkillFlux Bootstrap
  ├─ 授权计划、sha256 校验安装、精确版本锁和本地索引缓存
  ├─ 更新检查、固定版本、升级、回滚和移除
  └─ 向宿主返回需要的 Skill 文本
          ▲
          │ 用户明确调用
          ▼
用户的 AI 宿主完成原任务
```

公开内容通过构建发布；唯一的在线依赖是 GitHub raw 文件服务，不再有自托管后端。目录仓库的分支保护与 CI 一致性检查承担内容完整性防线；撤销与资格变化通过重建 index 反映到客户端与网站。

### 4.2 工程与存储划分

```text
skillflux/
├─ web/                 Astro 静态网站、页面组件、内容数据、发布脚本
│  ├─ data/             来源目录和公开发布快照
│  ├─ src/              页面、索引与交互
│  ├─ scripts/          同步、原子构建与浏览器验收
│  └─ tests/            单元与发布集成测试
├─ mcp/                 npm 包、CLI、本地 Runtime 与 MCP
│  ├─ src/runtime/      本地计划、安装、锁、更新和权限策略
│  ├─ src/catalog/      catalog build/scan：目录扫描、哈希、审核绑定校验、index 生成
│  ├─ skills/           显式 Bootstrap Skill
│  └─ tests/            协议、安全与运行时测试
└─ docs/                产品计划、运行说明和验收证据

skillflux-catalog/（独立 GitHub 仓库）
├─ skills/<category>/<id>/<version>/  skillflux.json + skillflux.review.json + 内容文件
└─ index.json              构建生成，客户端唯一入口
```

用户项目内的 `.skillflux/` 保存其本地配置、目录仓库钉扎、精确锁、缓存和已安装技能。目录仓库只包含允许公开的数据；私人评测材料不进入该仓库。

技术基线：Astro 静态构建，TypeScript，Node.js CLI，MCP SDK，SHA-256 内容摘要，git commit SHA 内容寻址。不为改版迁移到无必要的新前端框架。

### 4.3 目录仓库与数据边界

`index.json` 条目包含：技能摘要（id/version/name/description/category/tags/hosts/publisher/license/entry/permissions）、逐文件 `{path, sha256, size}`、release 元数据、quality 证据（自动检查 + 人工评测公开摘要 + review）、派生 qualification 与 status。免签名：完整性由 commit SHA 钉扎 + 逐文件 sha256 + CI `catalog build --check` 一致性保证。

不进目录仓库的数据：待审与驳回版本的私人评测材料、维护者私人笔记。公开 review 文件只含可公开摘要；`simulation` 评测不产生 qualified 派生状态。

### 4.4 静态发布与 SEO / AI 可读性

- HTML、详情、分类、标签、场景文章和机器索引来自一致的数据源。
- 提供 canonical、hreflang、结构化数据、sitemap、robots、`/index.json`、`/skills-index.json`、`/scenarios/index.json`、`/llms.txt`、`/llms-full.txt` 和已有 RSS。
- URL 中的交互筛选参数不制造无限数量的索引页；详情使用稳定规范地址。
- 旧运营页不进 sitemap；robots 不是身份验证或安全边界。
- 同步器从目录仓库拉取 index 与文件，校验逐文件哈希、版本资格、评测绑定和内容摘要。
- 目录仓库变更（批准、补测、撤销）后同步重建；不能指望静态站因仓库数据变化而自动改写已部署页面。
- 原子发布先在临时目录同步与构建，全部成功后一次切换当前版本；失败保留上一份有效站点和快照。
- 持续同步流程遇到失败记录错误并重试；相同 commit SHA 可以跳过，网站代码变化时可强制重建。
- 紧急撤销还需要处理部署端/CDN 缓存；不能声称已追回用户下载或模型已经读入的旧文字。

主要工程命令：

```bash
npm ci
npm run typecheck
npm test
npm run build
npm run pack:mcp
npm run smoke:package

# CATALOG_REPO 由运营者提供实际值：
npm run publication:sync --workspace @skillflux/web -- --repo CATALOG_REPO
npm run publication:build --workspace @skillflux/web -- --repo CATALOG_REPO
npm run publication:watch --workspace @skillflux/web -- --repo CATALOG_REPO --interval 60
```

命令中的大写参数名是待提供的实际运行配置，不是已存在的域名、密钥或对外发布状态。

### 4.5 安全与隐私

- 网络边界校验协议与地址；下载只发生在钉死 commit SHA 的 raw URL 上，拒绝重定向，限制响应大小与超时。
- 本地与远端文件操作防路径穿越、符号链接替换、特殊文件名和保留元数据路径覆盖。
- 内容哈希、不可变版本、计划绑定与项目锁共同保护安装；加载前检测本地篡改。
- HTML 和内嵌 JSON 正确转义，原始文本不能变成可执行脚本；私人评测不进公开产物。
- 长时间运行的 MCP 应重新读取项目权限策略，不继续使用已经被用户撤销的缓存授权。
- 搜索在本地索引缓存上进行，检索词不上传。

### 4.6 部署

- 网站部署至 Cloudflare Workers；技能内容托管于 GitHub 目录仓库，无自托管服务器。
- 目录仓库需配置分支保护与 CI；GitHub 账号安全（2FA）是内容信任根，须由维护者实际设置。
- 备份即 `git clone` 与 fork；撤销与历史回溯依赖 git 历史。
- 正式 npm 发布、域名部署、第一批真实精品评测都必须有实际配置与证据；不能用文档或测试样本代替。

## 5. 风险、执行顺序与验收（Risks & Roadmap）

### 5.1 主要风险与处置

| 风险 | 处置要求 |
| --- | --- |
| GitHub 账号或仓库被攻破 | 账号 2FA、分支保护、禁 force-push 为信任根的一部分；账号失窃即内容失窃，须立即撤销仓库并以新仓库重发 |
| 免签名模型下的索引篡改 | 客户端钉 commit SHA 下载、plan 绑定 indexSha256、CI `catalog build --check` 一致性门禁三重约束 |
| 国内访问 raw.githubusercontent.com 不稳定 | 客户端保留 `--source` 镜像参数；必要时为 skillflux.app Worker 增加透传缓存路由（后续决策） |
| 页面可抓取但未被收录 | 正确提供静态内容与索引，持续观察真实结果，不承诺训练、收录或排名 |
| 把扫描当成人测 | 分开保存自动与人工证据，评测绑定 contentHash，模拟记录不满足生产发布 |
| 历史版本无法补测 | 更新该版本目录的 review evaluation 并绑定当前 contentHash，保持原版本目录内容不变 |
| 用户项目被未授权升级或覆盖 | 默认手动、一次选择跟随策略、兼容边界、精确目标、固定策略、编辑保护与事务恢复 |
| 静态内容与目录仓库状态不同步 | 同步 + 原子重建、快照时间与 commit SHA、撤销发布与 Runtime 检查 |
| 测试样本被当成真实精品 | 隔离临时目录、明确标注、生产目录仓库不灌入合成审批 |
| 严格宿主拒绝含点号的 MCP 工具名 | 在四种目标宿主实测 `skillflux.*` 命名；如被拒绝改为 `skillflux_*` 下划线命名并同步文档与客户端 |

### 5.2 执行顺序

下列顺序用于控制依赖，不代表只交付某个缩减阶段：

1. 固定产品边界与公开/私密数据模型（本文件）。
2. 完成 catalog 模块：目录扫描、哈希、审核绑定校验与 index 生成（`skillflux catalog build`）。
3. 完成 npm、显式入口、本地 MCP、GitHub 源客户端、授权安装、更新维护和安全恢复。
4. 完成静态黄页、场景内容、精品版本页、机器索引和目录仓库同步的发布流水线。
5. 进行真实 GitHub 仓库、真实 MCP、干净 npm 安装、禁用 JS、移动端、异常与攻击式验收，修复发现的问题。
6. 核对正式配置与真实人工评测，再执行经授权的对外发布与运营。

不能把“功能已编码”“单元测试通过”“测试数据审批成功”和“真实业务已经上线”混为一谈。
