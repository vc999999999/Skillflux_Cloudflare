# Skill 更新、提醒与发布分工

适用客户端：`@skillflux/mcp` 1.2.0 起。更新日期：2026-10-11。

## 一份发布数据，两种提醒入口

技能版本与资格以 GitHub 目录仓库 `index.json` 为准。客户端直接读取目录；网站构建读取固定 commit 的完整快照，验证通过后生成页面与 RSS。不维护另一份“可更新版本”清单。

| 功能 | 触发点 | 做什么 | 是否改动已安装技能 |
| --- | --- | --- | --- |
| MCP 启动检查 | 每次 MCP 连接完成初始化后一次 | 后台检查当前项目已安装版本，通知待关注项 | 否 |
| `check_updates` / `check-updates` | 用户主动检查 | 返回版本、兼容性、固定状态、更新说明、来源和未知状态 | 否 |
| `load` + 默认 `manual` | 使用已安装技能 | 重新验证完整性与撤销状态，加载原版本并披露可用更新 | 否 |
| `load` + 已开启 `follow-compatible` | 使用已安装技能 | 经既有精确计划、依赖与哈希验证，事务安装允许的兼容更新 | 是 |
| 手动 `update` | 用户批准具体版本计划 | 按批准计划升级；仍保护固定版本与本地修改 | 是 |
| 版本 RSS | 站点发布后，由订阅器定时拉取 | 公告合格包的版本与更新说明 | 否 |
| 本地维护检查脚本 | 维护者运行脚本 | 检查上游来源变化，留待挑选与审核 | 否 |

RSS 不知道用户安装了哪些技能，也不计算项目兼容性。启动检查不是程序自更新，更不会替用户开启跟随策略。npm 只在客户端功能升级时需要更新；以后新增 Skill 包版本不需要为此发布 npm。

## 防止重复与竞争

- Runtime 的 `describeUpdates` 和既有兼容性判断是客户端版本结果的唯一来源。通知层只展示结果；RSS 只展示发布元数据。
- 同一 Runtime 同时发起的目录刷新共用一次请求和缓存写入。请求结束后，下一次 `load` 仍尝试实时检查撤销，不能用启动检查代替安全校验。
- 空项目启动不联网。初始化握手不等待检查；工具响应只读取已经完成的结果，不等待后台网络。
- 启动检查在网络请求后重新读取项目锁。通知发送前再比对锁修订号；安装、升级、固定或移除后过期的结果直接丢弃。
- 每次连接最多附带一次启动详细提示。`load` 或显式 `check_updates` 已经报告的同一版本状态从提示中排除；旧缓存结果不能覆盖随后到达的新结果。此规则不压制每次加载必须披露的撤销、未知与校验错误。
- MCP 日志是一条简短完成通知，详细结果由下一次成功工具响应补充，保留原 `structuredContent` 格式。宿主可能隐藏日志；没有工具调用时，不能保证用户看到详细提示。RSS 由订阅器自己的拉取周期决定提醒时间。
- 关闭 MCP 会取消启动请求并丢弃迟到的结果。离线检查报告 `unknown`；离线加载仍按既有规则只返回校验过的内容，不自动升级。
- 去重状态只在当前 MCP 会话内，不增加持久提醒数据库。下次启动可再次提醒尚未处理的更新。

## 发布到用户的流程

1. 运行本地维护检查脚本，挑选需要收录的变化。上游更新不等于自动批准发布。
2. 为所选 Skill 新增不可变版本目录，收录完整正文、脚本、模板、资源和依赖。填写版本说明、实际维护时间、破坏性变化和最低客户端版本。
3. 完成人工用途、边界、宿主验证，证据绑定内容哈希；重建 `index.json` 并通过目录验证。待验证收录不进入可安装发布清单或版本 RSS。
4. 推送目录 main 的 index 变化。目录 CI 验证成功后调用主站 Cloudflare Deploy Hook。站点构建重新解析目录 main、固定 SHA、验证全部发布快照并原子切换产物；失败保留上一份站点。
5. 核对线上版本页与 `/releases/feed.xml`，确认版本、说明和 GUID。主 `/feed.xml` 合并版本、资源和文章；`/insights/feed.xml` 只含文章。
6. 用户下次启动 MCP 获得只读提醒；主动检查获得完整差异。默认手动选择是否更新；开启跟随的用户在下一次加载时应用允许的更新。

版本 RSS 的 GUID 由目录仓库、Skill ID、版本组成，不使用构建时间、目录 commit 或整个快照哈希。同版本重建不会制造新公告；更改包内容必须发布新版本。每个 feed 保留最近 30 项，长期未拉取的订阅器不保证补齐全部历史。撤销会使版本退出合格发布清单，不能依靠 RSS 撤回已被阅读的内容；客户端加载时的撤销检查仍是必要环节。

## 升级已有客户端

```bash
npm install -g @skillflux/mcp@1.2.1
skillflux init --project /absolute/path/to/project --repo vc999999999/skillflux-catalog --host codex
```

使用项目原来的 repo、source 和 host 参数；本地安装用户在原安装目录更新 npm 包。重新初始化刷新受管理的 Bootstrap 和 MCP 配置，保留既有更新策略，再重启 MCP。自写且未标记的入口文件不会被覆盖。

不必为了获得提醒开启自动更新。需要自动跟随时，再明确执行 `skillflux update-policy follow-compatible --project /absolute/path/to/project`。

## 验证边界

自动测试覆盖启动不阻塞、空项目、并发检查、提醒去重、锁修订失效、关闭取消、离线未知，以及既有固定、回滚、篡改保护与兼容升级。打包测试从空目录安装实际 npm tarball，通过 stdio MCP 验证“旧版安装 → 新版目录 → 重启只提醒一次且不升级 → load 自动升级并返回新内容”。合成版本只存在于测试目录，不发布到真实目录。

网站测试验证只有合格发布项进入 RSS、新版本产生新 GUID、重建 GUID 稳定、时间排序与 XML 转义。线上验证应另行记录；不能用这些测试代替某个用户真实宿主或 RSS 账号收到通知的证据。
